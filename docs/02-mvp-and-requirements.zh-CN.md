# MVP：首个可验证的音乐数据 → 故事电台闭环

[English](02-mvp-and-requirements.md) | 简体中文

产品定义见[README](../README.zh-CN.md)，功能稳定 ID 与成熟度见[功能库](PRODUCT_FUNCTIONS.zh-CN.md)。这里专注**我们如何证明个人音乐数据确实提升了听众体验**，而不是把整个产品远景都变成 P0。

## P0 · 必须验证的能力

| 顺序 | 能力 | 可观察的验收结果 |
| --- | --- | --- |
| 1 | **导入真实曲库数据** | 至少接入一种用户授权的数据导出；展示歌曲、音乐人、专辑、歌单及可获得的播放次数、原始添加日期 |
| 2 | **数据质量与身份** | 展示每个字段的来源、缺失比例与统计口径；区分 Work/Recording/Release/Track；不把导入时间当添加日期 |
| 3 | **Personal Music Report** | 输出至少三条有数据或来源支撑的洞察，覆盖长期/短期兴趣与可解释音乐关系，不确定性可见 |
| 4 | **可信资料和 Context Pack** | 能为选题检索相关用户数据和音乐史依据，模型只看必要信息，不编造人名、参与关系与历史事实 |
| 5 | **节目策划** | 给出至少两个明显不同的候选故事，支持指定单曲/主题；每期有约 15–20 分钟目标、章节和歌曲可播状态 |
| 6 | **模块化节目制作** | 主持开场、串场、歌曲和结尾独立；TTS 可生成，并能在指定修改后复用不受影响的片段 |
| 7 | **实际播放或清晰降级** | 授权音源可用时真实播放；若只有元数据，准确标示为节目策划/主持预览，不伪装已播商业音乐 |
| 8 | **Music Assistant 复用验证** | 实测现成库、API、AI Radio Host/Show/Segment/播放队列及真实字段，形成“可直接复用/需要适配/需要开发”的报告 |
| 9 | **本地/云端 Provider** | 明确选择实际使用的 LLM/TTS、处理的数据和失败行为，不静默传输私人数据 |

## 验证时的关键比较

**A/B 对照：同一个节目主题，用通用音乐知识与加入真实个人音乐数据分别策划。** 至少检查四个维度：音乐事实正确性、与用户收藏的关联是否真实、叙事是否自然且有新发现、是否值得听完整期。

**数据审计：** 对选取的样本歌曲逐项核对平台 UI 与导出文件中的 Play Count、Date Added、曲名/音乐人/专辑；区分原始平台的累计次数与根据历史事件自行计算的次数。字段不全应明确反馈，而不是补零。

**模块化审计：** 给一档已拟定节目提出“换一种音乐人关系讲法”，记录改动了哪些脚本和 TTS 片段，哪些内容得到复用；不预设所有改动均能无缝衔接。

**版权与可播审计：** 对每种接入单独验证“能读取目录”“能播放完整歌曲”“能否混合音频”三种权限，不能以 Provider 存在或已登录代替能力证明。

## P1 · 首个闭环成立后的深化

扩展更多平台；完善长期音乐图谱、报告与编辑记忆；补充可选采访、声学分析、已完成节目收藏与更完整的前端交互。具体优先级要基于前述验证，而非一次承诺所有功能。

## 实施顺序与已知状态

先验证 **Apple Music Windows 曲库元数据及原始统计可获得性**，再做数据报告/选题，对照研究原版 Music Assistant AI Radio，最后按实际缺口补模块。界面先用黑白低保真草稿验证，避免为尚未证明的能力投入完整 UI 开发。
