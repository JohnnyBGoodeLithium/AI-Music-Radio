# 已明确方向与待决策问题

[English](05-open-questions.md) | 简体中文

**职责：** 只管理跨模块的产品/技术决策及待验证依赖。具体音乐样例、参演者和节目时间轴只存放于[Demo](03-my-back-pages-demo.zh-CN.md)。功能成熟度统一见[功能库](PRODUCT_FUNCTIONS.zh-CN.md)。

## 已明确的方向

- 产品由**私人音乐存储/服务器基础能力**和独立的 AI 音乐电台理解/播放层组成。
- 为制作首版电台，**不重造**通用 NAS、备份服务或完整音乐服务器。
- 输入是一首能确定身份的完整录音文件；必要身份缺失可报错，不做文件内对齐或指纹补全。
- 音乐理解结合**元数据/可信音乐知识**与具备权限时的**可选整曲声学分析**。
- **先从用户真实可播放的曲库召回**关联曲目，再解释关系证据、主观听觉观察和串场理由。
- 节目策划、主持稿、生成语音资产与合法歌曲播放必须分离。
- TextLLM/TTS **本地或云端显式选择**；不可静默上传私人数据或切换 Provider。
- 产品、架构、MVP、状态、示例和功能库各有唯一文档职责，中文与英文同期更新。

## 待验证的依赖

| 领域 | 问题 | 下一步验证 |
| --- | --- | --- |
| 存储 | **Lenovo Smart Storage** 是否有获授权的文件、目录或播放集成接口？ | 查产品/SDK 资料并实际测试，不能由“音乐分类”推断已有 API |
| 曲库服务 | 是否复用成熟的音乐服务器及其现有能力？ | 与本地目录基线比较可用适配方式 |
| 录音身份 | 哪些标签、置信度和数据库匹配足以确认 Recording？ | 测试同名曲、同作品不同版本等边界 |
| 声学提取 | 哪些整曲特征真实有价值且允许分析？ | 少量本地 DSP 测试及听感复核 |
| 候选推荐 | 如何平衡翻唱、合作等有据关系、声学相似、个人偏好与节目多样性？ | 建立候选排序及解释评价 |
| 节目质量 | 怎样避免“歌手百科朗读”，形成真正好听的策展节目？ | 多类型音乐的人工试听 |
| 模型 Provider | 本地/云端文本及 TTS 怎么达到质量、成本、隐私目标？ | 可控 A/B 测试与数据出端审计 |
| 播放 | 每种后端支持何种完整文件播放、许可与安全访问？ | 用具有合法权限的文件测试 |
| 用户体验 | Owner、Explorer、Listener 哪类用户最有长期价值？ | 分别验证三种主路径，而不是按流派想象 |

## 隐私与版权

**用户合法拥有且可播放的音乐文件**可以摆脱持续流媒体订阅；这不代表零运营成本、能访问所有云端目录或获得商业 DRM 音频的抓取、裁切与再编码许可。公开仓库不得包含私人曲库、收听历史、凭据或未经许可音频。

## 下一决策节点

等小型本地曲库与可播放节目闭环成立之后，再选择进一步适配 (a) Lenovo Smart Storage、(b) 成熟音乐服务器，或 (c) 继续直接读取文件。通过 Adapter 隔离，避免此决定迫使 AI 电台核心重写。
